统一资产模型 · 原始示意

说明「一张表 + 多个广场入口」是什么意思。这是草稿示意，不是最终 UI。技术图：index.html · 功能图：functional.html

一句话：MCP、Skills、知识库、插件、模型、Runtime 在后台看起来像多个菜单，但数据库里先共用同一张资产主表。 公共字段管「是谁的、哪个版本、能不能用」；每种类型自己的细节塞进 spec（JSON）。 这样后面加新类型主要是加 kind，不用每样资源各造一套完全不同的表和权限模型。

1. 公共字段 vs 各自细节

所有资产都有的字段（核心）

id主键
tenant_id租户
kind类型：mcp / skill / …
name显示名
version如 1.0.0
statusdraft / published / …
visibilityprivate / tenant / public
owner_id创建人
updated_at时间

按 kind 变化的字段（spec JSON）

mcpendpoint、tools 列表、风险等级
skill入口、依赖、安装包引用
knowledge_base外部引擎、外部 ID、绑定方式
plugin平台 Manifest、签名、兼容版本
modelbase_url、路由、配额策略引用
runtimeHermes 地址、健康检查 URL
↓ 同一张表里的不同 kind（示意数据）
mcp
gfast.question.create业务 Tool，经治理门调用
skill
office-doc-gen平台定义，再投影给 Hermes
knowledge_base
课程教材库只登记 + 绑定 WeKnora
plugin
browser-pack平台 Manifest，不是 Hermes 私有格式
model
deepseek-chat路由 ID，密钥不进广场明文
runtime
hermes-local第一步就要登记

你在菜单点「知识库」，其实是 WHERE kind = 'knowledge_base'；点「MCP」就是 kind = 'mcp'。不是五套无关系统。

3. 一条资产长什么样（示意 JSON）

{
  "id": "ast_01H...",
  "tenant_id": "tenant_demo",
  "kind": "mcp",                 // 换 kind 就是另一种广场资源
  "name": "gfast.question.create",
  "version": "1.0.0",            // 已发布版本尽量不可变
  "status": "published",         // draft → review → published
  "visibility": "tenant",
  "owner_id": "user_01",
  "spec": {                      // 只有这类资源关心的细节
    "transport": "gfast-internal",
    "risk_level": "L1",
    "input_schema": { "...": "..." }
  }
}

第一步编码：先落这张主表 + 后台列表/新建（MCP + Runtime）。Skills/知识库/插件菜单可以先占位，点进去提示「二阶段页面」也行。
